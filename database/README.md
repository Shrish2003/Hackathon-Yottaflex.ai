# Database Tier: O2C Revenue Assurance Platform

The `database/` tier establishes a dedicated, decoupled database architecture layer for the Order-to-Cash (O2C) Revenue Assurance and Revenue Leakage Detection Platform.

---

## 1. Purpose of the Database Tier

In our three-tier enterprise architecture:
- **`frontend/`** — Presentation Layer (React 18 + Vite + Tailwind CSS)
- **`backend/`** — Application and Business Logic Layer (FastAPI + SQLAlchemy 2.x + Detection Engine)
- **`database/`** — Relational Persistence, Schema Migrations, and Diagnostics Layer (PostgreSQL + Alembic + SQL Diagnostics)

The `database/` tier isolates:
1. Version-controlled schema migrations (`migrations/`).
2. Read-only SQL diagnostic and audit scripts (`sql/`).
3. Seed generation workflows and documentation (`seeds/`).

---

## 2. Database Technology & Design

- **RDBMS Engine:** PostgreSQL 15+ (Production instance: PostgreSQL 18.6)
- **Database Name:** `o2c_revenue_db`
- **Default Port:** `5432`
- **Default Host:** `127.0.0.1`

### Relational Schema Design
The schema models the full Order-to-Cash (O2C) commercial lifecycle with referential integrity:

1. **Master Data:**
   - `accounts` (Customer master, credit limits, payment terms)
2. **Commercial Quoting & Ordering:**
   - `quotes` & `quote_lines`
   - `sales_orders` & `order_lines` (Direct link to quotes, line quantities, unit prices, discounts)
3. **Fulfillment:**
   - `shipments` & `shipment_lines` (Dispatched quantities, tracking references, carrier data)
4. **Billing & Invoicing:**
   - `invoices` & `invoice_lines` (Billed revenue, tax, lines linked to shipments/orders)
5. **Treasury & Remittance:**
   - `payments` (Remittances received, unallocated cash)
   - `payment_allocations` (Line-item or invoice-level settlement links)
6. **Dispute Management:**
   - `disputes` (Customer billing disputes, amounts, resolution states)
7. **Lifecycle Audit Trail:**
   - `status_events` (Immutable state transition logs with timestamps)
8. **Revenue Assurance & Leakage Detection:**
   - `exception_records` (Identified policy violations, financial leakage amounts, recommended actions)
   - `exception_evidence` (Substantiating forensic evidence payloads and conflicting record links)
9. **Internal Evaluation (Isolated):**
   - `ground_truth_anomalies` (Ground-truth dataset reserved strictly for offline benchmark evaluation; never exposed via runtime APIs or frontend)

## 3. Schema Migrations (Alembic)

Alembic schema migrations are centralized under `database/migrations/`:

```
database/migrations/
├── env.py              # Environment configuration hooking into SQLAlchemy metadata
├── script.py.mako      # Template for autogenerated revisions
└── versions/           # Version-controlled migration scripts
    ├── ecd9b80ec8db_create_o2c_core_tables.py
    ├── 2114b193a45a_add_ground_truth_anomalies_table.py
    └── a862bb2a11e5_add_exception_records_and_evidence_tables.py
```

### Inspecting Migration History
From the `backend/` directory (or pointing `alembic` to `backend/alembic.ini`):

```powershell
cd backend
.\.venv\Scripts\alembic.exe current
.\.venv\Scripts\alembic.exe history
```

Current revision head: `a862bb2a11e5 (head)`.

### Applying Migrations
To upgrade the database to the latest revision:

```powershell
cd backend
.\.venv\Scripts\alembic.exe upgrade head
```

## 4. Synthetic Seed Data Workflow

Seed data is generated through the modular synthetic generator in `backend/app/generators/`.

- **Deterministic Seeds:** Seeded with constant `20261022` and deterministic `UUIDv5` hashing for repeatable runs.
- **Dependency Ordering:** `Accounts` → `Quotes` → `Sales Orders` → `Shipments` → `Invoices` → `Payments` → `Payment Allocations` → `Disputes` → `Status Events`.
